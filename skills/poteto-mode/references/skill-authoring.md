# Pi skill authoring procedure

Local replacement for Cursor's unavailable create-skill dependency. Use for new skills, substantive edits, and description tuning; it does not install skills or promise automatic model evaluation.

1. Establish scope from the user's request and concrete examples. Record desired inputs, outputs, approvals, failure handling, and non-goals. Read the existing skill and structural sources before drafting. Ask about unresolved behavior rather than inventing policy.
2. Draft `<kebab-name>/SKILL.md` with YAML frontmatter containing `name` (matching the directory) and a quoted, single-line `description`. Escape quotes and backslashes; quote values containing YAML punctuation. For this package include `disable-model-invocation: true`; do not add unknown keys or change hidden discovery policy. Put instructions after the closing `---`. Store supporting detail in linked relative references rather than duplicating it.
3. Write the smallest executable procedure: entry conditions, ordered actions, authority boundaries, verification, and final output. Preserve existing approvals. Use installed Pi capabilities only; consult [runtime adaptations](herdsman-runtime.md) before adding delegation or scheduling. Run `/skill:unslop` on the draft without removing behavioral constraints.
4. Build a small case table before revising: representative intended requests, ambiguous requests, and nearby requests that must not select this skill. Include expected decisions and outputs, plus a failure/approval case. Walk each case through the instructions; for structural edits add or update executable tests for links, metadata, and affected behavior. Run available validators and this package's `npm test`. Record actual results separately from prose walkthroughs. Model trials require authorization and an available runner; never fabricate trial results.
5. Tune the description against the case table: name the task and discriminating user phrases, remove overbroad claims, inspect false positives and missed cases, revise once, and rerun the same cases plus one held-out case. Stop when the cases agree or after two revision rounds; report unresolved ambiguity for user judgment. Hidden skills remain explicitly invoked: this checks descriptive fit, not automatic invocation accuracy. If authorized model trials are available, compare baseline and revised descriptions with the same cases and report measured outcomes, not assumed gains.
6. Review the diff for unintended scope expansion, validate frontmatter with the installed loader/validator when available, check every relative resource link, and summarize changes, cases, results, and limits. Return to the authoring playbook for the PR step; do not install or publish without explicit authority.
