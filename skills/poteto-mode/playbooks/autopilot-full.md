### Autopilot-full

Before unattended execution, read and satisfy all four checks in [Unattended trust preflight](autonomous-run.md#unattended-trust-preflight). Missing checks block unattended work, but may be established through authorized attended preparation. This grants no additional scheduling, publication, scope, or tools authority and does not gate normal attended work.

**Adapter boundary.** Use bounded leaf assignments, not persistent actors or nested controller workflows. PR ownership below describes responsibility across phases, not one leaf running controller skills. After each implementation handoff, the lead orchestrates no-comments, interrogate, trail review and watcher delegation, supplies required skill/rubric evidence explicitly through files, and integrates asynchronous results before assigning the next bounded phase. Leaves do not launch reviewers or watchers. The lead dispatches independent review and subsequent phases. Competing checkouts require explicitly prepared external worktrees and separate lead sessions; direct delegates share the lead cwd. Do not pass model/tools/cwd/worktree/schema in agent requests. When only dependent agent work remains, end the turn and yield; integrate asynchronous results and forward exact result refs through files. These constraints govern the workflow below.

Use [Herdsman runtime](../references/herdsman-runtime.md) for supported launch, wake, isolation, and stop semantics. A written goal or cadence is not a running scheduler.

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges until your independent verifiers have proven the code that lands.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps verification, countersigns, and audits.

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. Shipping's patch-id and lane-result reuse rule can carry a lane's result, and every new head needs its own green CI.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When she asks for the protocol or plan to be stated, deliver the statement and stop. Execution starts only on the operator’s explicit go. Record the full program objective in the decision trail so it survives context changes.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One logical owner lane per PR uses bounded assignments to the matching implementation profile from the runtime role table for implementation, authorized pushes/PR operations, self-proof, local cleanup and triage. After the implementation handoff, the lead owns no-comments and interrogate review, supplying needed skills/rubrics through files, and dispatches the babysit watcher separately. Leaf assignments receive local deslop and trail-writing instructions explicitly; they do not invoke controller workflows. The lead integrates each result before authorizing the next phase, including any rebase or merge permitted by this playbook. Within about 15 minutes, every owner starts a `decisions.tsv` trail through `/skill:show-me-your-work`, pushes its first branch snapshot, and opens the PR ready, never draft. After each verifiable unit, push the authorized branch again with hooks on; a WIP commit is acceptable. A new independent queue item gets a fresh bounded assignment with consolidated scope. Before every round-starting push, run the pre-review checks named by the repo's AGENTS.md files and rules for touched paths on the committed head. Return the commands, outcomes and committed head SHA as receipts. A hook pass is not proof. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. Externalize every kept unit and handoff promptly in the authorized store or branch so a replacement can recover it: exact assignment/session identity, branch and head, last owned remote SHA, current base, state, receipts, blockers and next bounded phase. Do not add a push grant where none exists. Force-push only the owned branch with `--force-with-lease=refs/heads/<branch>:<last-owned-SHA>` after checking the remote; an unexpected push stops the lane for ownership resolution. An explicitly handed-over root push establishes the next lease. Rebase onto current trunk before code-ready and babysit; keep that base during fix rounds unless trunk conflicts or breaks CI, or merge prep requires a rebase. When shipped code is final after cleanup and lead-owned no-comments review, report the code-ready head SHA and the SHA of each later patch-changing push. Report merge-ready with its exact head SHA only when self-proof, CI and the lead-owned babysit phase are complete. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel off trunk, never stacked.** Many owners at once when PRs are self-contained. Use one writer per branch, disjoint files, and authorized rebases to absorb cross-PR drift. Only genuinely overlapping work serializes. Independent PRs branch straight off trunk. Sequenced work is merge then branch; dependent base-branch chains use [Autopilot-stack](autopilot-stack.md), not a private exception.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single independent verifier at the new head. Fan out parallel independent verifiers at the code-ready SHA per `/skill:swarm` and aggregate to one verdict. The lanes re-run the gates at that SHA, prove load-bearing behavior on the project's verification skill, and audit the receipts and diff instead of trusting the PR body. Require at least two independent focused audit lanes, each with the full brief and receipts. Give each lane one main focus, such as consumer parity, races, or data/config safety. Include a regression lane against trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for. The live lane is the floor. Record a defect proven on trunk independently of the PR against trunk; it does not gate the PR unless copied or newly reached by the PR. Keep regression proof and all PR-owned findings gating. No merge without the root's clean verdict. Audit the merge-ready report's receipts before the verdict. The lead consolidates every proven finding into one fix-forward to the owner. A behavior defect filed as a note is still a finding. For each behavior finding, require a red test covering every site with the same defect, or a reproduction receipt when no test can demonstrate it. Carry each defect into the next round's review brief. Give the next bounded assignment the consolidated findings and proof requirements; retain applicable results only under the patch-id and lane-result reuse rule in `playbooks/shipping.md`, with current-head CI and mergeability.
5. **On a clean verdict the owner merges, and a fresh assignment takes the next item.** Merge preparation starts only after the round's verification lanes start. Rebase onto current trunk, report the resulting head SHA, and require CI on that exact head. Preserve applicable results only under the patch-id and lane-result reuse rule in `playbooks/shipping.md`. A later trunk move alone need not force another rebase. Immediately before merge, fetch trunk and require a clean `git merge-tree` against the head. Compare `git diff --name-only $(git merge-base HEAD origin/main) origin/main` with the PR's changed paths and all paths that determine its CI selection. If there is an overlap or conflict, rebase again unless the lockfile-only exception below proves safety; report the new SHA, require CI on it, and repeat these checks. Re-verify any changed patch. Also inspect caller and dependency changes, not just overlapping files: run the patch's checks on the merge result when trunk changed a caller, called code or dependency version. Record the tested merge-result SHA and receipts. A shared lockfile may avoid an overlap-driven rebase only with an authorized frozen install on the merge result and proof that the PR's changed packages resolve as on its head; failed or unavailable proof requires the rebase. This exception never bypasses a conflict, current-head CI, mergeability, or the applicable step 4 verification. If trunk would require a third merge-preparation rebase, hold and report so the root can sequence colliding work. The lead integrates proof and authorizes the bounded merge phase only with an independent clean verdict and the operator's merge grant. The owner merges through the resolved forge using [Shipping](shipping.md)'s installed-command validation and merged-state/trunk-base readback, then returns. A fresh bounded assignment takes the next independent item. Operator-named items wait at merge-ready for the operator.
6. **Run the root layer.** Any new loosening of a gate, budget or allowlist needs verifier proof and then your fresh countersign, only within the operator's approval grant; otherwise hold for the operator. Absorbing already-landed values is drift, not new permission to loosen a gate. Do not disable or soft-fail a check to get green; restore its guarding behavior within authority. Never give or bypass an approval enforced by the forge. Run an audit tick over all owners every hour with a separately installed and explicitly authorized scheduler. If none is available, record periodic unattended auditing as blocked; Herdsman settlement is not a timer. Re-read this playbook from the current trunk path `skills/poteto-mode/playbooks/autopilot-full.md`, re-read the stored program objective and plan from the decision trail, then audit the operation against both inputs and correct drift during this tick. Inspect decision trails for the authorized audit; do not poll active agents for progress. Count only side effects as progress: commits, pushes, PR or check deltas, and stored reports. Inactivity is advisory, not proof of a hang. For a required control decision use only the exact live label and current available_tools. Steer changes work non-preemptively; interrupt cancels the current operation; close intentionally abandons work. Preserve identity, partial diffs and cleanup evidence; resolve pending controls and mailbox issues, confirm teardown and release of write ownership before replacement. Unknown teardown blocks replacement; do not silently retry or take over unresolved work. When merges batch, run a retro pass and a post-merge bot-comment sweep. A material operator-facing update uses [Ketchup](../../ketchup/SKILL.md); an unchanged audit tick stays quiet, with the tick and evidence recorded in the trail.
7. **Stand down instantly on the operator's stop.** The operator’s hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** use [Ketchup](../../ketchup/SKILL.md) for user outcomes, PR states and verdicts, merges, countersigns and reasons, and open operator gates. Link PRs and decision trails. Keep exact head SHAs, owner assignments and swarm receipts in the linked durable record; include them in the reply only when needed to act.
