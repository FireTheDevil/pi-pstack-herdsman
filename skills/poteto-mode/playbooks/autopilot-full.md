### Autopilot-full

**Adapter boundary.** Use bounded leaf assignments, not persistent actors or nested controller workflows. PR ownership below describes responsibility across phases, not one leaf running controller skills. After each implementation handoff, the lead orchestrates no-comments, interrogate, trail review and watcher delegation, supplies required skill/rubric evidence explicitly through files, and integrates asynchronous results before assigning the next bounded phase. Leaves do not launch reviewers or watchers. The lead dispatches independent review and subsequent phases. Competing checkouts require explicitly prepared external worktrees and separate lead sessions; direct delegates share the lead cwd. Do not pass model/tools/cwd/worktree/schema in agent requests. When only dependent agent work remains, end the turn and yield; integrate asynchronous results and forward exact result refs through files. These constraints govern the workflow below.

Use [Herdsman runtime](../references/herdsman-runtime.md) for supported launch, wake, isolation, and stop semantics. A written goal or cadence is not a running scheduler.

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When she asks for the protocol or plan to be stated, deliver the statement and stop. Execution starts only on the operator’s explicit go. Record the full program objective in the decision trail so it survives context changes.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One logical owner lane per PR uses bounded assignments to the matching implementation profile from the runtime role table for implementation, authorized pushes/PR operations, self-proof, local cleanup and triage. After the implementation handoff, the lead owns no-comments and interrogate review, supplying needed skills/rubrics through files, and dispatches the babysit watcher separately. Leaf assignments receive local deslop and trail-writing instructions explicitly; they do not invoke controller workflows. The lead integrates each result before authorizing the next phase, including any rebase or merge permitted by this playbook. Within about 15 minutes, every owner starts a `decisions.tsv` trail through `/skill:show-me-your-work`, pushes its first branch snapshot, and opens the PR ready, never draft. After each verifiable unit, push the authorized branch again with hooks on; a WIP commit is acceptable. A new independent queue item gets a fresh bounded assignment with consolidated scope. Before every round-starting push, run the pre-review checks named by the repo's AGENTS.md files and rules for touched paths on the committed head. Return the commands, outcomes and committed head SHA as receipts. A hook pass is not proof. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. The rebase always precedes babysit and never waits for drift or conflicts. When shipped code is final after cleanup and lead-owned no-comments review, report the code-ready head SHA and the SHA of each later patch-changing push. Report merge-ready with its exact head SHA only when self-proof, CI and the lead-owned babysit phase are complete. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained. Use one writer per branch, disjoint files, and rebase to absorb cross-PR drift. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main. Sequenced work is merge then branch. One exception is an owner that must split a genuinely dependent change and can hold a short private base-branch stack.
4. **Swarm-verify code-ready work and every later changed patch before merge.** At the owner's code-ready head SHA and each later push that changes the patch, fan out parallel independent verifiers per `/skill:swarm` and aggregate to one verdict. The lanes re-run the gates at that SHA, prove load-bearing behavior on the project's verification skill, and audit the receipts and diff instead of trusting the PR body. Require at least two independent focused audit lanes, each with the full brief and receipts. Give each lane one main focus, such as consumer parity, races, or data/config safety. Include a regression lane against trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for. The live lane is the floor. No merge without the root's clean verdict. The lead consolidates every proven finding into one fix-forward to the owner. A behavior defect filed as a note is still a finding. For each behavior finding, require a red test covering every site with the same defect, or a reproduction receipt when no test can demonstrate it. Carry each defect into the next round's review brief. Give the next bounded assignment the consolidated findings and proof requirements; retain a verdict across a SHA-only rebase only under the patch-id and current CI rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges, and a fresh assignment takes the next item.** Merge preparation starts only after the round's verification lanes start. Rebase onto current trunk, report the resulting head SHA, and require CI on that exact head. Preserve a code verdict only under the stable patch-id rule in `playbooks/shipping.md`. A later trunk move alone need not force another rebase. Immediately before merge, fetch trunk and require a clean `git merge-tree` against the head. Compare `git diff --name-only $(git merge-base HEAD origin/main) origin/main` with the PR's changed paths and all paths that determine its CI selection. If there is an overlap or conflict, rebase again, report the new SHA, require CI on it, and repeat these checks. Re-verify any changed patch. The lead integrates proof and authorizes the bounded merge phase only with an independent clean verdict and the operator's merge grant. The owner squash-merges through the resolved forge and returns. A fresh bounded assignment takes the next independent item. Operator-named items wait at merge-ready for the operator.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value needs your fresh countersign, granted only after verifier proof. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour with a separately installed and explicitly authorized scheduler. If none is available, record periodic unattended auditing as blocked; Herdsman settlement is not a timer. Re-read this playbook from the current trunk path `skills/poteto-mode/playbooks/autopilot-full.md`, re-read the stored program objective and plan from the decision trail, then audit the operation against both inputs and correct drift during this tick. Inspect decision trails for the authorized audit; do not poll active agents for progress. Count only side effects as progress: commits, pushes, PR or check deltas, and stored reports. Inactivity is advisory, not proof of a hang. For a required control decision use only the exact live label and current available_tools. Steer changes work non-preemptively; interrupt cancels the current operation; close intentionally abandons work. Preserve identity, partial diffs and cleanup evidence before replacement; do not silently retry or take over unresolved work. When merges batch, run a retro pass and a post-merge bot-comment sweep.
7. **Stand down instantly on the operator's stop.** The operator’s hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh assignment took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
