### Autopilot-stack

**Adapter boundary.** Use bounded leaf assignments, not persistent actors or nested controller workflows. PR ownership below describes responsibility across phases, not one leaf running controller skills. After each implementation handoff, the lead orchestrates no-comments, interrogate, trail review and watcher delegation, supplies required skill/rubric evidence explicitly through files, and integrates asynchronous results before assigning the next bounded phase. Leaves do not launch reviewers or watchers. The lead dispatches independent review and subsequent phases. Competing checkouts require explicitly prepared external worktrees and separate lead sessions; direct delegates share the lead cwd. Do not pass model/tools/cwd/worktree/schema in agent requests. When only dependent agent work remains, end the turn and yield; integrate asynchronous results and forward exact result refs through files. These constraints govern the workflow below.

Use [Herdsman runtime](../references/herdsman-runtime.md) for supported launch, wake, isolation, and stop semantics. A written goal or cadence is not a running scheduler.

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack the operator reviews and lands.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One logical owner lane per PR uses bounded assignments to the matching implementation profile from the runtime role table for implementation, authorized pushes/PR operations, self-proof, local cleanup and triage. After the implementation handoff, the lead owns no-comments and interrogate review, supplying needed skills/rubrics through files, and dispatches the babysit watcher separately. Leaf assignments receive local deslop and trail-writing instructions explicitly; they do not invoke controller workflows. The lead integrates each result before authorizing the next phase, including any rebase or merge permitted by this playbook. Within about 15 minutes, every owner starts a `decisions.tsv` trail through `/skill:show-me-your-work`, pushes its first branch snapshot, and opens the PR ready, never draft. After each verifiable unit, push the authorized branch again with hooks on; a WIP commit is acceptable. A new independent queue item gets a fresh bounded assignment with consolidated scope. Before every round-starting push, run the pre-review checks named by the repo's AGENTS.md files and rules for touched paths on the committed head. Return the commands, outcomes and committed head SHA as receipts. A hook pass is not proof. Report the code-ready head SHA when shipped code is final and STACK-READY with its exact head SHA only when proof, CI and the lead-owned babysit phase finish. Report each later patch-changing push SHA. Keep the trail uncommitted and return it in the report.
2. **Audit with an authorized scheduler.** The root runs an audit tick every hour with a separately installed and explicitly authorized scheduler. If none is available, record periodic unattended auditing as blocked; Herdsman settlement is not a timer. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from current trunk at `skills/poteto-mode/playbooks/autopilot-stack.md`, re-read the stored program objective and plan from the decision trail, audit the operation against both inputs, correct drift during this tick, and inspect decision trails without polling active agents. Count only side effects as progress, such as commits, pushes, PR or check deltas, and stored reports. Inactivity is advisory, not proof of a hang. For a required control decision use only the exact live label and current available_tools. Steer changes work non-preemptively; interrupt cancels the current operation; close intentionally abandons work. Preserve identity, partial diffs and cleanup evidence before replacement; do not silently retry or take over unresolved work.
3. **Hold the operator gates.** State then wait, so a request to state the plan is not a go. On the operator’s explicit go, record the full program objective in the decision trail. The objective continues across turns until the chain is done. On the operator’s stop, every owner takes an immediate zero-writes hold.
4. **Verify at code-ready and every changed patch through STACK-READY.** The owner reports the exact head SHA. The root swarm-verifies code-ready and later patch-changing pushes using `/skill:swarm`. Parallel independent verifiers re-run the gates at that SHA, prove the load-bearing behavior through the project's verification skill, and audit receipts and diff instead of trusting the PR body. Require at least two independent focused audit lanes, each with the full brief and receipts and one main focus. The swarm aggregates to one verdict. The lead applies Autopilot-full step 4's complete fix-forward procedure, including every proven finding, behavior defects filed as notes, red tests across every site with the same defect or reproduction receipts, and defects carried into the next review brief. Nothing enters the stack unverified; a SHA-only rebase retains its verdict only under step 7's patch-id and current CI rule.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>` according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at old SHAs. Compare the stable `git patch-id` for each PR's base-to-head diff at its verdict SHA against its new base-to-head diff. An unchanged patch-id preserves the code verdict. Any changed patch goes back through step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it with her own clicks or with merge-when-ready the operator arms.

**Choosing between the autopilots.** Use Autopilot-full when PRs are independent and landing authority is granted. Use Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
