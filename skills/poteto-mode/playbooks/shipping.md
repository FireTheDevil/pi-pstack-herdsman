### Shipping

Use [Herdsman runtime](../references/herdsman-runtime.md) for supported launch, wake, isolation, and stop semantics. A written goal or cadence is not a running scheduler.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after `playbooks/babysit.md`. Work only within explicit rebase, push, retarget and merge grants. Freeze the verified bottom-to-top list and its ceiling before landing. Once landing starts, the sanctioned post-merge child move below is the only topology change; mid-landing fixes require the operator's go. Keep one branch/topology writer and resolve ownership before switching writers.

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR view, watch, edit, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One subagent per PR, not batched, each a Pi background subagent, each exercising the real surface through the project's verification skill or harness against parent versus head. This is an independent landing check, not a reduction of an execution playbook's full-swarm requirement at code-ready and for new behavior, a redesign, or a large new diff. Rebases, merge-conflict resolutions and minor fixes get a single independent verifier at the new head under that cadence. Each returns `PASS`, `PASS+NOTES` or `FAIL` and, when publication is authorized, posts that verdict on its own PR; otherwise returns it to the lead for the authorized record. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable. Report the ceiling as the highest PR in the contiguous passing run and name the first gap. An independent PR whose branch neither contains nor needs the lower code may be extracted onto trunk only with authority and a fresh independent verdict; its old parent-based verdict is not enough.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, compare the recorded patch-id with its current base-to-head patch-id. Re-verify when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. Require fresh current-head CI and mergeability even when a lane's result survives.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push only within its ownership grant, and retarget only that PR to trunk with `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Re-run step 3 after the push. Once current-head CI is green and the applicable verdict results survive step 3, a later trunk move need not force another rebase. Immediately before landing, fetch trunk, require a clean git merge-tree against the head, and confirm that trunk changes since the merge base touch neither PR paths nor paths that determine its CI selection. If either check fails, rebase again unless the lockfile-only exception below proves safety; require CI on the new head, repeat these checks, and re-verify any changed patch. For every rewritten push, check `ls-remote` against the recorded last-owned remote SHA and pin `--force-with-lease=refs/heads/<branch>:<last-owned-SHA>`; stop on an unexpected push, even if a fresh fetch would make an unpinned lease pass. Check caller and dependency changes and test the merge result as required by [Autopilot-full step 5](autopilot-full.md), including its bounded frozen-install lockfile exception and third merge-prep rebase hold. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** Only with explicit merge authority and a clean independent verdict, merge the bottom PR. Confirm the installed forge's documented command and policy before use: upstream Origin uses plain `origin pr merge <pr>` and may merge every PR below the named PR, while GitHub uses `gh pr merge <pr> --squash`. Never target above the current bottom or assume Origin supports GitHub's flags. If requirements are still running and the user asked for merge-when-ready, arm only that PR, using the installed Origin's documented `--auto` form or `gh pr merge <pr> --squash --auto`. Verify its current head and surviving verdict before arming; auto-merge lands whatever head becomes ready. Origin's `--auto` is Origin merge-when-ready. GitHub's `--auto` is GitHub auto-merge. Read back the actual forge state and trunk base after the command. Success, a queue entry or an auto-merge request is not a merge. Wait for confirmed merged state with trunk as base before preparing the next one; unknown state blocks advancement.
6. **Do not read GitHub `autoMergeRequest` as stack readiness.** At most it says GitHub auto-merge was requested for one GitHub PR. It does not prove Origin merge-when-ready is armed, that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. Confirm the active forge's state for the current bottom PR, and say that the state is unknown if the active forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm merged state, trunk base and the merged SHA's presence, then drop the merged PR from the frozen bottom-to-top list. If that verified run is now empty, go directly to step 9 without retargeting, rebasing, pushing or otherwise mutating any descendant. Otherwise inspect the new bottom PR's base, head, checks, and patch-id. Retarget only that next verified child to trunk with the resolved forge, move only its patch onto the confirmed merge result, and push with step 4's explicit lease and ownership checks. A host may retarget automatically, but verify rather than assume. This post-merge move is the only sanctioned chain mutation during landing. Recompute the child's base-to-head patch-id against its recorded verdict and require fresh current-head CI and mergeability; verify any changed patch under the execution playbook's cadence and step 3's lane-result reuse rule. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** With Origin, use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then re-read the PR until it reports merged or blocked. With GitHub, use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` only as an event wake and poll `gh pr view <pr> --json state,mergedAt,baseRefName,mergeStateStatus,statusCheckRollup,autoMergeRequest` after each wake, ignoring `READY` until `mergedAt` is non-null or `state` is `MERGED`. Require trunk as the reported base and then run step 7 to confirm the merge result's presence. Hard-fail only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE` or `CANCELLED` and blocks merge after auto-merge is no longer pending, or `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition here. Hold the watch under a nonblocking `pstack-verifier` task that runs the real watcher and reports its verdict through Herdsman settlement. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
